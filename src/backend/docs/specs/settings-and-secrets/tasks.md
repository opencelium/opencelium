# Settings and secrets: the tasks

Each task is 1 pull request. The size rule of a task is in CONTRIBUTING.md, section 5.3.
The status line is the only status in this folder.
A task that changes the behaviour of a criterion changes spec.md in the same PR.

## Task 1: feat(core): read the settings of the installation as an admin
- **Criteria:** SS-01, SS-05, SS-06
- **Function:** An admin of a self-host installation reads the settings of the broker connection and sees the default of each one. An OpenCelium user without the admin role, and each user in the cloud mode, gets `access-denied`. This task declares the 4 settings of the broker connection without the password; task 3 declares the password. SS-05 and SS-06 get their tests of a change in task 2.
- **Tests:** `SettingRegistryTest` (unit): constructorStopsWithTheSettingKeyWhenTwoDefinitionsDeclareIt, definitionGivesTheDefinitionWhenTheSettingKeyIsKnown, definitionIsEmptyWhenNoFeatureDeclaresTheSettingKey, definitionsGivesEachDeclaredSettingWhenTheRegistryHasDefinitions; `InstallationAdminTest` (unit): checkPassesWhenTheUserHasTheAdminRoleInTheSelfHostMode, checkRefusesWhenTheUserHasNoAdminRole, checkRefusesWhenTheModeIsCloud; `SessionTokensTest` (unit): authenticationOfGivesEachRoleAsAnAuthorityWhenTheSessionJwtHasRoles; `SettingsEndpointTest` (full application): getGivesTheDefaultOfEachSettingWhenTheDatabaseHasNoValue, getGivesTheDatabaseValueWhenTheDatabaseHasOne, getKeepsTheSettingsCollectionEmptyWhenAnAdminReadsTheSettings, getGivesAccessDeniedWhenTheUserHasNoAdminRole, getGivesStatus401WithoutABodyWhenTheRequestHasNoToken; `SettingsCloudTest` (full application): getGivesAccessDeniedWhenTheModeIsCloud
- **Hand test:** 1. Start core on the database `oc_hand` as in task 2 of the authentication tasks. 2. Log in as `admin` with `POST /api/auth`, and copy `sessionJwt` into the shell variable `T`. 3. Run `curl -s localhost:9090/api/settings -H "Authorization: Bearer $T"`. 4. The response has the 4 broker settings, each with `"default": true`, and the port `5672`. 5. Run `mongosh oc_hand --eval 'db.settings.countDocuments()'`: it prints 0. 6. Run `mongosh oc_hand --eval 'db.users.updateOne({username: "admin"}, {$set: {roles: []}})'`. 7. Log in again and do step 3 with the new session JWT. 8. The status code is 403, with the code `access-denied`.
- **Size:** approximately 350 lines. The task adds the package `core.authz`, the authorities of `core.auth`, the access-denied handler of the main chain and the session-JWT fixture of `testsupport`.
- **Depends on:** nothing
- **Status:** done

## Task 2: feat(core): change and reset the settings of the installation
- **Criteria:** SS-02, SS-03, SS-04, SS-05, SS-06
- **Function:** An admin changes or resets the broker settings through the settings API, and the next read through each core instance gives the result. A request with an unknown setting key or an incorrect value changes nothing and names each incorrect key. SS-02 and SS-04 get their tests of a secret setting in task 3.
- **Tests:** `SettingTypeTest` (unit): validateAcceptsAPortWhenItIsFrom1To65535, validateRefusesAPortWhenItIs0, validateRefusesAPortWhenItIs65536, validateRefusesAPortWhenItIsAString, validateRefusesAPortWhenItHasAFraction, validateAcceptsAHostNameWhenEachLabelHas63CharactersOrLess, validateRefusesAHostNameWhenALabelHas64Characters, validateAcceptsAnIpv4Address, validateAcceptsAnIpv6Address, validateRefusesATextWhenItHasMoreThan255Characters; `SettingsServiceTest` (full application): changeSetsEachNewValueWhenEachValueIsValid, changeRemovesTheFieldWhenTheNewValueIsTheDefault, changeChangesNothingWhenOneValueIsNotValid; `SettingsEndpointTest` (full application): patchGivesTheNewValueWhenTheValueIsValid, patchGivesInvalidSettingsWithEachIncorrectKeyWhenAKeyIsUnknown, patchChangesNoSettingWhenOneOfTwoValuesIsNotValid, patchResetsTheSettingWhenTheValueIsNull, patchGivesBadRequestWhenTheBodyIsNotAJsonObject, patchGivesAccessDeniedWhenTheUserHasNoAdminRole; `SettingsCloudTest` (full application): patchGivesAccessDeniedWhenTheModeIsCloud; `SettingsInstancesTest` (full application): getGivesTheNewValueWhenAnotherSpringContextChangedIt
- **Hand test:** 1. Start core and log in as in task 1, with the session JWT in `T`. 2. Send `PATCH /api/settings` with `{"broker.host": "rabbit.internal", "broker.port": 5673}` and the header of `T`. 3. The response shows the 2 new values with `"default": false`. 4. Send `PATCH` with `{"broker.port": "abc", "broker.vhost": "x"}`. The key `broker.vhost` is not a setting key. 5. The status code is 400, with `invalid-settings` and the 2 keys in `errors`. 6. Read the settings: the port is still `5673`. 7. Send `PATCH` with `{"broker.port": null}`, then read the settings. 8. The port is `5672` with `"default": true`. 9. Run `mongosh oc_hand --eval 'db.settings.find()'`: the document has only `broker.host`.
- **Size:** approximately 300 lines
- **Depends on:** 1
- **Status:** open

## Task 3: feat(core): keep the broker password as an encrypted secret
- **Criteria:** SS-02, SS-04, SS-07, SS-08
- **Function:** An admin sets and resets the broker password through the settings API. The database keeps only its ciphertext, and each response shows the mask. The task adds the secret contract of `common`, the secret storage, and the DEK access that the signing-key loader also uses.
- **Tests:** `SecretReferenceTest` (unit): toStringShowsTheOwnerAndTheIdAndNoValueWhenItIsPrinted, equalsIsTrueWhenTheOwnerAndTheIdAreTheSame; `SecretCipherTest` (unit): encryptUsesANewIvWhenItRunsTwice, decryptGivesThePlaintextWhenTheOwnerTheIdAndTheVersionAreTheSame, decryptStopsWhenTheSecretIdIsDifferent, decryptStopsWhenTheOwnerIsDifferent, decryptStopsWhenTheCiphertextIsChanged; `DekAccessTest` (full application): useGivesTheSystemDekWhenTheOwnerIsSystem, useStopsWhenTheOwnerHasNoDek; `MongoSecretStorageTest` (full application): storeKeepsOnlyTheCiphertextWhenItStoresASecret, readGivesThePlaintextWhenTheSecretIsStored, deleteRemovesTheDocumentWhenTheSecretIsStored; `SettingsEndpointTest` (full application): patchShowsTheMaskWhenTheBrokerPasswordIsSet, getShowsTheMaskWhenTheBrokerPasswordIsSet, getShowsNullWhenTheBrokerPasswordIsNotSet, patchDeletesTheCiphertextWhenTheBrokerPasswordIsReset, patchDeletesTheReplacedCiphertextWhenTheBrokerPasswordChanges, patchWritesNoPlaintextToACollectionOrTheLogWhenTheBrokerPasswordIsSet; the tests of `SigningKeyLoaderTest` pass on the DEK access.
- **Hand test:** 1. Start core and log in as in task 1, with the session JWT in `T`. 2. Send `PATCH /api/settings` with `{"broker.password": "s3cret-hand"}`. 3. The response shows `"****"` for `broker.password`. 4. Run `mongosh oc_hand --eval 'db.settings.find()'`: the password field holds a reference, not the text. 5. Run `mongosh oc_hand --eval 'db.secrets.find()'`: 1 document with a ciphertext. 6. Search the application log for `s3cret-hand`: there is no match. 7. Send `PATCH` with `{"broker.password": null}`. 8. Run `mongosh oc_hand --eval 'db.secrets.countDocuments()'`: it prints 0.
- **Size:** approximately 380 lines. The secret storage and the secret setting stay in 1 task: the storage alone has no caller, and the plan names no seam between them.
- **Depends on:** 2
- **Status:** open
